# Cardbe 企業版：下一階段開發計畫

日期：2026-11-05。狀態：待實作的工作計畫。

依據目前 `enterprise/phase-1` 副本、[實作進度](enterprise-progress.md)與[原型限制](../enterprise-server/README.md)。本文件接續[完整企業版計畫](enterprise-plan.md)，不代表完整企業版已完成。

## 1. 下一個交付目標

**先完成能用公司帳號登入、資料存入 PostgreSQL 的內部在線試用版，再接入桌面離線同步。**

第一輪先花兩週驗證登入與資料交易的完整流程。成功後，擴充成可供 3–5 位內部成員使用的受控測試環境；桌面同步完成並驗收後，仍須補齊原計畫其餘 P0，包括團隊收件匣、垃圾桶、排程備份、整合政策與平台交付，才能進入原計畫的 10–30 人試點。

目前先沿用單一組織私有部署、一個 OIDC 身分提供者、Windows 主平台與 Ubuntu beta 的方向。個人模式仍可離線使用，個人資料不會自動上傳。

## 3. 第一輪：兩週技術驗證

假設兩位全職工程師，分別負責身分／介面及資料／交易；若只有一人，先完成交易契約與 PostgreSQL 流程，再做 OIDC，依實際投入重排。以下是排程假設，不是交付承諾。

| 時段       | 身分／介面工作                                          | 資料／交易工作                                                                               | 可檢查的成果                                       |
| ---------- | ------------------------------------------------------- | -------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| 第 1–2 天  | 定義 principal、IdP 綁定、session、裝置與組織成員的關係 | 定義交易邊界、授權排序、穩定操作 ID 與模型對照                                               | 架構決策、API／錯誤契約、隔離測試案例              |
| 第 3–5 天  | 接一個隔離測試 IdP，走通登入、callback、登出            | 建 PostgreSQL migration 與最小儲存介面，移植建立任務、帶 `base_version` 的標題更新及快照讀取 | 可重現的登入示範與 PostgreSQL 資料寫入             |
| 第 6–8 天  | 介面接 session；驗證過期、錯誤 issuer、帳號切換         | 補上交易內授權、receipt、稽核與撤權競爭測試                                                  | 用本人登入身分建立任務；重送不重複、撤權後不能提交 |
| 第 9–10 天 | 合併端到端驗證、錯誤畫面與文件                          | 服務重啟、併發、交易失敗與乾淨資料庫重建                                                     | 示範、測試報告、未解事項及下一輪估算               |

兩週只驗證最小流程，不要求一次移植所有管理 API，也不要求完成正式部署或桌面同步。

**第一輪示範情境：**兩位測試成員分別登入同一個受管理看板，A 建立任務；模擬成功回覆遺失並重送，只產生一筆任務。服務重啟後資料仍在。B 被撤權後，以原 session 寫入或讀取該板遭拒；已接受操作的 receipt 也不能繞過當下權限。

## 4. 從技術驗證走到在線內部版

這個里程碑暫估合計 **6–10 週，包含前兩週**，假設兩位全職工程師且有可用的測試 IdP。第二週結束後依實測重新估算；不包含完整企業 MVP。

### PostgreSQL 與交易

- 從現有 `store.rs` 抽出必要的業務規則與儲存邊界；先服務當前 API，避免一次重寫全部桌面 domain。
- 移植組織、工作區、成員、裝置、看板 ACL、任務、留言、operation receipt 與稽核。以同一套行為案例驗證現有原型及新 adapter，不要求長期維護兩種正式服務資料庫。
- 明確設計撤權與寫入的交易排序、版本前提、唯一鍵及有限次重試。驗收以撤權交易提交完成後開始的請求必須被拒絕為底線；已在途的操作須有可重現的先後順序。
- 使用兩個獨立資料庫連線測試同時重送、版本競爭、撤權／寫入與交易失敗；不能沿用單一 Mutex 的結果宣稱支援併發。
- 將工作區、看板及成員等管理建立操作納入重送策略；不能只對任務命令去重。
- 正式測試環境預設建立新資料庫。若需搬移原型資料，另做一次性匯入工具，保留 ID、關聯與 receipt；舊開發 token 不轉成正式憑證。未確認需求前不碰原型或桌面資料庫。

PostgreSQL 的交易隔離與失敗重試有不同語義，這是遷移時要重新驗證併發行為的依據。[官方交易隔離文件](https://www.postgresql.org/docs/current/transaction-iso.html)

### 登入、成員與裝置

- 首版只接一個已設定的 IdP；採 Authorization Code 流程，記錄 callback、state、nonce、PKCE 與憑證驗證策略。驗證 issuer、audience、簽章與期限，使用成熟程式庫。
- 用 `issuer + subject` 綁定內部穩定身分，email 僅作顯示／邀請線索。先做受控加入與綁定，不自動依 email 網域授予組織角色。
- 瀏覽器由服務端完成登入並建立可撤銷 session；採安全 cookie、CSRF 防護及明確來源限制，移除正式模式的貼 token 登入。IdP token 不落入瀏覽器持久儲存。
- 成員自行註冊裝置；正式模式關閉管理員替成員簽發登入憑證的能力。保留有明確程序與稽核的 Owner 恢復方案，補上 Owner 交接與最後一位 Owner 的限制。
- 每次業務交易重新檢查本服務的 session、membership 與板級權限。本服務停權不能只等 JWT 到期。
- 額外決定 IdP 停權如何傳入本服務，例如支援的事件通知或定期重新驗證，並量測最長生效時間；完成 OIDC 登入不等於已完成 IdP 離職停權同步。

身分綁定及 token 驗證依據 [OpenID Connect Core](https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation)。具體登入與 session 架構是本專案的規劃選擇。

### 部署與維運

- 提供單組織測試部署：服務、PostgreSQL、靜態管理介面、TLS 入口與設定範本；介面不再依賴 Vite dev server。設定固定版本與 secrets 注入方式。
- 設計部署模式的 Host／Origin allowlist 與可信 proxy 邊界；不能直接把目前 loopback 原型改為對外監聽就視為完成部署。
- 補健康檢查、資料庫就緒狀態、migration 狀態、結構化錯誤紀錄與登入／API 速率限制。
- 建立備份與空環境還原流程，核對任務、留言、權限、receipt 與稽核。還原後失效既有 session，重新確認成員權限；不能讓舊備份恢復已撤銷的存取。
- 補 Windows 回歸、Linux `.deb` 打包及安裝測試；依實際可取得的桌面環境測 X11／Wayland、輸入法、托盤、通知與 deep link，記錄尚未驗證的項目。

### 在線內部版的退出條件

1. 在全新測試環境依文件即可部署，正式模式不接受開發 token。
2. 3–5 位內部成員以自己的帳號完成登入、授權、任務指派與留言。
3. 停權、裝置撤銷、板級撤權、帳號切換及跨組織／跨板負向測試通過。
4. 多連線交易測試證明資料、receipt 與稽核一致；網路不確定結果不造成重複建立。
5. 完成一次可驗證的備份還原；沒有未處理的資料遺失或越權問題。
6. 說明資料量、測試硬體與已知限制；不以單機原型的測試結果推論容量或正式支援範圍。

## 5. 再下一階段：桌面離線同步

桌面同步的完整接入依賴穩定身分、服務端交易與任務契約；技術風險原型可提前進行。工期在第一輪驗證後重估，仍沿用完整計畫的獨立同步階段，不納入上述 6–10 週。

首個交付範圍限定為：**一個受管理看板、兩位成員、兩台桌面、任務與留言**。

| 工作           | 必要行為與驗收                                                                                         |
| -------------- | ------------------------------------------------------------------------------------------------------ |
| 桌面登入       | 系統瀏覽器登入與 PKCE；憑證由桌面 Rust 端及系統秘密儲存管理，登入不依賴嵌入式 WebView                  |
| 資料來源與隔離 | 明確區分 Local／Peer／Managed；企業快取綁定服務、組織與使用者，帳號切換不讀取或代送前一人的資料        |
| 本機待送佇列   | 已確認狀態與待送操作分開持久化；operation ID 與內容固定，桌面重啟後可重送；本機提交與入列具原子性      |
| 增量同步       | 服務端同交易寫入變更紀錄；提供分頁游標、快照及過期游標重建；授權變更也能使客戶端更新存取狀態           |
| 衝突與撤權     | 首輪沿用明確的版本衝突，讓使用者保留草稿並選擇處理；被拒絕操作不混入已確認狀態，也不自動搬至個人工作區 |
| 入口盤點       | 企業板的 UI、MCP、外掛、搜尋、匯出與分享逐一驗權；尚未接入共同提交流程的寫入功能先對企業板停用         |
| 介面與 Undo    | 顯示待同步、已同步、需登入、衝突、撤權；企業 Undo 未有安全反向操作前先停用，個人模式維持原行為         |

桌面登入的系統瀏覽器與 PKCE 方向依據 [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252)。離線撤權只能阻止後續服務端存取，無法保證立即抹除裝置已下載的內容。

首輪不自動轉換現有個人／P2P 看板。Flow、全域便箋、附件、重複任務等需各自有模型與同步驗證，未支援時在企業模式清楚標示；避免以簡化任務模型悄悄丟失欄位。後續再逐步抽出桌面與服務端共用的領域規則。

**同步退出條件：**A 離線修改後關閉程式，重開並連線只提交一次；B 的後續變更不被舊快照覆寫；A 若已遭撤權，待送操作被拒絕且有明確處理狀態。快照重建、帳號切換與恢復服務後的重新授權均須通過。

## 6. 開工前需要落定的參數

規劃先依下列假設推進。尚未取得公司環境時，技術驗證可使用隔離的測試 IdP 與合成資料；接入真實組織前再填入實際配置。

| 項目     | 暫定方向                       | 何時必須確定                                           |
| -------- | ------------------------------ | ------------------------------------------------------ |
| IdP      | 一個 OIDC 提供者；受控成員加入 | 第一輪真實登入驗證前，需要測試租戶與註冊配置           |
| 部署     | 單組織私有部署                 | 在線內部版整合前，需要測試主機、網域、TLS 與維運負責人 |
| 人力     | 兩位全職工程師與必要的審查支援 | 排定日期前；若不同就重算，不沿用日曆工期               |
| 主平台   | Windows 主平台，Ubuntu beta    | 桌面同步驗收前，需要可操作的實體／虛擬桌面測試環境     |
| 離線政策 | 保留受管理離線能力，期限待定   | 桌面佇列與快取政策實作前                               |

本輪規劃僅新增文件與導覽；尚未安裝 PostgreSQL、註冊 IdP、變更依賴、公開服務或改動應用程式行為。
